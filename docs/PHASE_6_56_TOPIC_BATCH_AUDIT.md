# Phase 6.56 continuation — topic duplicate guard and generation batch audit

**Status:** implementation started on branch `phase-6-56-topic-batch-audit`; this is a scoped increment inside Phase 6.56, not a new numbered phase.

**Canonical status:** [Phase Registry](PHASE_REGISTRY.md)

## Scope

1. Compare each generated Q&A against existing Q&A for the same canonical concept and language, including pending and rejected rows, not only the current generated batch.
2. Use deterministic Unicode-preserving similarity triage on the question and answer pair. A candidate is a near-duplicate only when both the question and answer are sufficiently similar, or the combined pair crosses the stronger threshold. A different concept or language is not suppressed.
3. Retain the existing exact content-hash/database unique constraint as the final concurrency-safe duplicate guard. Similarity is an additional pre-save quality filter, not a replacement.
4. Return separate batch-audit counts: generated by provider, rejected by quality/evidence gates, duplicates, pending review and verified. Keep `saved_count` for compatibility.
5. Generation remains author-only and all new records remain `NEEDS_REVIEW`; `verified_count` is zero for generated candidates. Only the existing independent reviewer endpoint may verify a candidate.

## Safety and limits

- Existing topic records are read through the canonical repository (`verified_only=False`) with a 5,000-row safety bound. If that scan fails or exceeds the cap, generation fails closed before saving candidates.
- No candidate content is published to learners by this change. The learner read API remains VERIFIED-only.
- Similarity scoring is deterministic triage, not semantic truth validation. It may still require a human decision for borderline pairs and does not prove complete examinable-point coverage.
- Source URL/evidence requirements, bounded editor-supplied source text, exact quote checks, importance threshold and secure admin token remain unchanged.
- No schema migration is expected; no live database migration or secret is changed by this code slice.

## Regression coverage

- Existing pending rows suppress similar Q+A candidates for the same topic/language.
- Different concepts or languages do not suppress candidates.
- Similar phrasings within the same generated batch are counted as duplicates.
- Batch audit separates generated, rejected, duplicate, pending-review and verified counts.
- A failed existing-topic scan prevents persistence.
- Exact-hash/database deduplication and NEEDS_REVIEW-only behavior remain covered.
